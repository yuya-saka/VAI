# 2026-07-01 Work Log

## Stage2 骨折分類アーキテクチャ再設計

### 背景

既存`train_models/stage2/`は、Stage1の分類経路を残してRegion branchを追加した
モデルではなく、別の分類経路へ変更した独立モデルだった。

```text
Stage1:
CNN最終1280次元特徴
-> BiLSTM
-> 15断面logit
-> 15断面それぞれにBCE
-> 15断面のsigmoid平均

既存Stage2:
CNN中間特徴
-> FPN
-> Region pooling / Global pooling
-> 別のBiLSTM
-> 断面logitを損失計算前に平均
-> 椎骨単位logitにだけBCE
```

つまり既存Stage2には、Stage1の`1280`次元最終特徴を使うBiLSTM/head、
15断面それぞれのBCE、15断面のsigmoid平均による主予測が存在しない。
Region機構自体が誤りという意味ではなく、今回求める
「Stage1を維持してRegion補助branchだけを追加する比較実験」になっていないため、
Stage2を設計し直す方針を確定した。

### 確定アーキテクチャ

1つのEfficientNetV2-Sを共有し、以下の2経路へ分岐する。

#### Stage1主経路

- CNN最終`1280`次元特徴を使用
- Stage1と同じ2層BiLSTMと断面分類head
- 出力は15断面logit
- 椎骨ラベルを全15断面へ展開してweighted BCE
- 主となる椎骨確率は15断面のsigmoid平均

#### Region補助経路

- Region maskはCNN入力へ追加せず、空間特徴のPoolingだけに使用
- CNN中間4段階特徴をFPN風に`56x56`へ融合
- 各断面・各領域でmask-normalized pooling
- 領域特徴の形状は`[B, 15, 4, C]`
- 領域間で重み共有するBiLSTM/headから`[B, 15, 4]`のlogitを出力
- 各スライス内で4領域をstable Noisy-OR
- Noisy-OR後の各スライス確率へ椎骨ラベルBCE
- 15断面間はNoisy-ORせず、有効断面の確率平均を補助椎骨出力とする

### 損失

```text
L_stage1 = mean_s weighted_BCEWithLogits(z_stage1[s], y)

p_any[s] = 1 - product_r(1 - sigmoid(z_region[s, r]))

L_region = mean_valid_s weighted_BCE(p_any[s], y)

L_total = L_stage1 + lambda_region * L_region
```

- 領域ラベルは存在しない
- 各領域logitへ椎骨ラベルを直接与えない
- Region出力は校正済み確率ではなく、弱教師の領域エビデンスとして扱う
- 主評価はStage1経路の確率を使用し、Region経路は補助評価とする

### Region ID

実際の`region_4class.npy`の意味は以下。

```text
1 = body
2 = right_foramen
3 = left_foramen
4 = posterior
```

現行Stage2の水平反転mapping
`[0, 2, 1, 4, 3]`は古い領域定義用で誤っている。
修正値は`[0, 1, 3, 2, 4]`。

### 技術検証

`timm==1.0.22`の`forward_intermediates(indices=(1, 2, 3, 4))`を確認した。

- 1回のCNN forwardからFPN用4段階特徴を取得可能
- 同時に最終`1280`チャネル特徴mapを取得可能
- `forward_head(final_map, pre_logits=True)`でStage1と同じ`1280`次元特徴を取得
- 通常のStage1 forward出力との最大差は`0.0`

したがって、CNNを二重実行せずStage1主経路とRegion補助経路を構築できる。

  → `amp_initial_scale`は実質未使用、`max_consecutive_amp_skips`による
  リトライ猶予も到達しない分岐（非有限勾配が出た瞬間に`FloatingPointError`）。
- これは今回のStage2再設計で触った箇所ではなく、既存の`_amp_settings`/
  GradScaler構築/勾配チェックロジックそのまま（Stage1にはこの仕組み自体が
  存在しない＝Stage1は暗黙的にFP16固定でGradScalerの自動skipに任せている）。
- BF16はGradScalerの自動保護が効かないため、非有限勾配で即エラーにする
  現在の設計は「NaN混入を隠さず即座に検知する」という意味で妥当と判断。
  **現状維持でユーザー合意済み**。今回のスコープ外として変更しない。

### GPU学習時間の実測（RTX A6000）

実機ベンチマーク（batch_size=16, n_slices=15, in_channels=6, image_size=224,
bf16 AMP, backbone=tf_efficientnetv2_s）:

| | Stage1 (TimmModel) | Stage2 (新設計) |
|---|---|---|
| 学習1step (fwd+bwd+opt) | 414.8ms | 593.8ms |
| 推論のみ1step | ~144ms(概算) | 206.9ms |

Region補助branch追加で**1stepあたり約1.43倍**。実データ件数
（`region_4class.npy`ありの学習可能アイテム=13,929件、Stage1時点の11,263件と
近い規模）から1foldあたり約5〜6.5時間（40〜65epoch想定、単一GPU）、
5fold逐次で約25〜30時間と見積もった。

3×RTX A6000での並列化を検討:
- fold単位で3並列（`--start-fold`/`--end-fold`を分けて3プロセス手動起動）
  → 5foldは2巡必要なので総時間 ≈ 2 × 5〜6.5時間 ≈ **10〜13時間**
- 1foldをDDPで3GPU分担（`training.n_gpu: 3`）→ 1fold ≈ 1.8〜2.5時間、
  ただしfold自体は逐次にしかならないので合計はほぼ同じ ≈ **9〜12.5時間**
- 総時間はどちらもほぼ同じ。fold単位並列の方がDDPの複雑さがなくシンプル。

### 実際の学習実行時に見つかった挙動（DDP world_size=2）

ユーザーが`training.n_gpu: 2`で`train.py`を実行し、起動ログで以下を確認:

- `[INFO] excluded_studies=...`/`excluded_levels=...`/`Stage2 items=...`、
  およびtimmのHF Hub警告が**2回ずつ出力される**。原因は`train.py`の
  `_run_training()`が`collect_items()`を各DDP rankで独立に呼んでおり、
  `collect_items`/`_load_exclusions`内のprintがrank0限定になっていないため
  （`[INFO] Stage2 item collection completed in Xs`のみrank0限定）。
  今回の再設計より前からある既存挙動で、正しさに影響はないが
  ログノイズと軽い無駄（アイテム収集10秒×rank数）がある。
- `fold=0 train_batches=268 val_batches=134 world_size=2`の意味を検証:
  - `train_batches`は`DistributedSampler`で2GPUに分割された**rankごとの**
    バッチ数（8586件 ÷ 2 ÷ batch16 ≈ 268、drop_last込みで計算一致）。
  - `val_batches`は`create_data_loaders`の`val_loader`に`DistributedSampler`
    が付いていないため、**各GPUが検証セット2144件を丸ごと重複評価**している
    （2144÷16=134と一致）。結果は両rankで同一になるはずで正しさには影響
    しないが、計算が無駄に倍かかる。
- **未対応**: rank0限定logging化、val_loaderへの`DistributedSampler`追加は
  ユーザーに提案したが、次回セッション以降の判断待ち（まだ着手していない）。
