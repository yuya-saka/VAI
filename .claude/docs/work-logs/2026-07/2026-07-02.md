## Stage2学習の速度改善（NFS I/Oボトルネック解消 + augmentation集約）

### 背景

`train_models/stage2`の学習が遅い。`num_workers`はNFS I/O負荷のため
これ以上増やせないという相談から着手。

### 調査結果

- データセット`data/rsna_data/fracture_dataset`（study×vertebra、
  1サンプル=`ct.npy`3.76MB+`vertebra_mask.npy`0.75MB+`region_4class.npy`0.75MB
  ≈5.27MB）はNFS4共有マウント（`172.26.68.101:/share`、使用率86%）上にあり、
  `num_workers`を増やしても速くならないのはI/Oバウンド（NFSバウンド）が
  原因と判断。
- このマシンのローカル資源: `/dev/shm`(tmpfs, 126GB空き),
  `/home`(NVMe, 822GB空き), `/data2`(xfs, 5.9TB空き)。`/`はNVMeだが
  97%使用中で使用不可。
- `dataset.py`の`_augment_volume`は15断面をPythonループで回し、
  各断面で`ReplayCompose`を実行（1断面目のreplayを14断面に再生）。
  ベンチマークで125.7ms→77.6ms/sample（約1.6倍）にできることを確認。

### 実装1: ローカルステージング（`stage_to_local`）

`train_models/stage2/src/staging.py`を新規実装。

- `sweep_stale_stages(stage_root)`: 起動時に、PIDが死んでいる
  `vai-stage2-data-<uid>-<pid>`ディレクトリを掃除（SIGKILL/電源断からの
  回収用）。
- `stage_dataset(source_dir, stage_root)`: 必要な3ファイルのみ
  （`ct.npy`/`vertebra_mask.npy`/`region_4class.npy`、`seg_*.npy`や
  `sampling_qc.json`は対象外）をThreadPoolExecutor(32並列)でコピー。
  コピー前に`shutil.disk_usage`で空き容量を検査し、必要量×1.2倍
  マージンに満たなければ`RuntimeError`。
- `cleanup_stage(stage_dir)`: `shutil.rmtree(ignore_errors=True)`。
  `None`や二重呼び出しでも安全。

`train.py`の`main()`に統合:

- `data.stage_to_local: true`のとき、`mp.spawn`前（親プロセスで1回だけ）
  ステージし、`try/finally`で必ず`cleanup_stage`を実行。
  正常終了・例外・Ctrl+C（SIGINT→KeyboardInterrupt）で確実に削除される。
- `SIGTERM`はデフォルトだと`finally`を通さず即終了するため、
  `signal.signal(SIGTERM, _raise_on_sigterm)`で`SystemExit`に変換し、
  `finally`を通すようにした。
- **重要な設計判断**: ステージング先パス（PIDを含み実行毎に変わる）を
  `config["data"]["dataset_dir"]`へ書き込まない設計にした。代わりに
  `dataset_root: Path`を`_run`/`_run_training`へ別引数として渡す。
  理由: configを書き換えると、保存される`config.yaml`やcheckpointの
  `config`フィールド、`--resume`時の`validate_resume_config`比較が
  実行毎に変わるステージングパスに汚染され、再現性が壊れる／
  誤って「設定不一致」でresumeが弾かれるバグになるため。
- `experiment.py`の`_RESUME_ENV_ONLY_PATHS`に`data.stage_to_local`/
  `data.stage_root`を追加（環境系knobとしてresume比較から除外。
  ただし上記の設計によりconfigが汚染されないので実害は元々ない、
  将来ユーザーが値を変えてresumeする場合の保険）。
- `config/stage1_parity.yaml`に`stage_to_local: false`（既定オフ）、
  `stage_root: "/dev/shm"`を追加。
  **ユーザーが`stage_to_local: true`に変更済み**（本セッション中に
  ファイルが外部更新されたことを確認、意図的な変更として尊重）。

容量検証: 実データ全体（42,083ファイル、74.06GB）に対し
`/dev/shm`の空き135.17GB（検証時点）を確認、20%マージン込みの
必要量88.87GBでも余裕で収まることを確認済み。

### 実装2: augmentation集約（15回→1回）

`dataset.py`の`_augment_volume`を書き換え。

- `ct(15,5,H,W)`→`(H,W,75)`、`vertebra_mask`/`region_mask`(15,H,W)→
  `(H,W,15)`にスタックし、`self.transform`を1回だけ呼ぶ。
  `(2,3,0,1)`という転置が自己逆変換であることを利用し、往復の
  reshape/transposeで元の軸順に戻す。
- **検証で判明した副次効果**: 元のper-plane replay方式は、
  `GaussNoise`等のノイズを**全15断面に同一パターンで使い回して
  いた**（plane間diff=0を実験で確認）。スタック方式は
  `per_channel=True`の設定により75チャンネル各々に独立ノイズが
  乗るため、断面間のノイズ相関という意図しない副作用が解消された
  （plane間diff最大90を確認）。幾何変換（Affine/Distortion）は
  全チャンネル一括で同一変換が適用されるため、断面間の空間整合性
  という設計意図は維持される。

## Stage2 2GPU学習が epoch1 開始直後にフリーズする問題の修正

### 背景

上記のステージング/augmentation改善後、`outputs/baseline/v1`
（`config/parity.yaml`使用、`n_gpu: 2`, `batch_size: 8`）で2GPU実行したところ、
fold0のepoch0（train+valid）は完走したが、epoch1のtrain開始直後
（`0/536 [00:00<?, ?it`）でプロセスが完全に停止。GPU使用率も含めて
一切進捗しなくなった。

### 原因調査

`train_models/stage2/src/trainer.py`の`train_one_fold`を確認:

- validation（`evaluate()`）は`if is_main:`（rank0限定）でのみ実行されるが、
  渡している`model`は`DistributedDataParallel`でラップされたままだった。
- DDPは既定で`broadcast_buffers=True`のため、evalモードのforwardでも
  BatchNorm running statsをrank0→全rankへbroadcastする集団通信が
  毎バッチ発行される。Stage2Modelは`tf_efficientnetv2_s`
  （BatchNorm2d多数）+ `BatchNorm1d`ヘッド（`model.py`）を持つため該当。
- rank1はvalidationをスキップし、fold終端の
  `dist.broadcast(stop_tensor, src=0)`まで先に到達して待機。
- 結果、rank0が発行する「バッファbroadcast×268回（val_batches）」と
  rank1が発行する「stop broadcast×1回」がNCCL上で発行順にのみ
  マッチングされ、サイズ・型不一致のまま通信ストリームが恒久的に
  ズレてepoch1最初のforward/backwardでデッドロック。観測された
  症状（valid完走→train1が0/536で凍結）と一致。

### 修正内容（`train_models/stage2/src/trainer.py`）

1. `DistributedDataParallel(..., broadcast_buffers=False)`を追加
   （validationがrank0限定である以上、forward毎のバッファ同期は
   不要かつ有害なため無効化）。
2. 毎エポックのvalidation呼び出し（`train_one_fold`内、epochループ）で
   `model`→`_base_model(model)`に変更し、DDPラップを外した素の
   モデルで評価するよう修正。
3. fold終了後のbestモデル再評価（同関数末尾）も同様に
   `_base_model(model)`へ変更。ここはrank1が既に`return`して
   次foldのDDP構築（パラメータbroadcast）へ進んでいるタイミングの
   ため、DDPのまま評価すると同種の不整合が再発し得る。

`ruff check` / `ruff format --check`は`trainer.py`に対してpass。
ユニットテストでは2GPU DDPのデッドロックは再現しないため、
実機での2GPU再実行が唯一の検証手段。

### 検証結果

修正後、`outputs/baseline/v1`を再実行（`config/parity.yaml`、
`--resume`なしの新規run、wandb run `20260702_182957`開始）。

- epoch1以降も正常に進行を確認。19:24時点でfold0のepoch0〜12
  （13epoch）完走、GPU 0/1とも94〜97%使用率を維持しフリーズなし。
- ペース: wandb開始からepoch12完走まで約54分34秒/13epoch
  ≈ **4.2分/epoch**（修正前の単epoch実測4分41秒よりやや高速化、
  broadcast_buffers=False化による通信オーバーヘッド削減と整合）。
- 学習挙動: train/val lossとも単調減少、`amp_skipped_steps=0`が
  全epochで維持（NaN/inf勾配なし、bf16 AMP安定）。
  val AUROCは0.670（epoch0）→0.849（epoch11、現時点best）と
  順調に改善、epoch12時点でpatience=1（`early_stopping_patience: 15`）。
