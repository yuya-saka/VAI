## 1. bbox↔スライス対応の全数検証（問題なし）

## 2. 骨折椎体の見落としを発見（本題）

ユーザー指摘「骨折bboxがあるはずの椎体に、bboxが無いことになっていないか」を受けて
`train.csv` の椎体別骨折ラベルとツールの実run構成を突き合わせ。

- **骨折ラベル=1なのにrunが1つも無い椎体: 25件 / 235 study**
- 原因: 前処理metadataの `assigned_bbox_slice_numbers` がDICOM z範囲だけで椎体を
  割り当てるため、頸椎が湾曲し隣接椎体のz範囲が重なる箇所でbbox行が別椎体へ
  誤って割り当てられる（例: study 19778 で C4 mask z=[169.4,192.9] と C5 mask
  z=[152.9,179.4] が10mm重複）。
- 全235 study・全7,217行 × 7椎体の被覆率総当たりで内訳を確定:
  - 割当level == 最大被覆level: 6,247行 (86.6%)
  - 不一致だが最大被覆levelにも既存runがある（別runに紛れているだけ）: 374行 (5.2%)
  - **不一致かつ最大被覆levelにrunが無い（見落とし本体）: 487行 (6.7%)**
    - うち骨折ラベル=1（真の見落とし）: **9件・40行**
    - うち骨折ラベル=0（骨折していない椎体への単純なはみ出し）: 92件・447行
  - どのmaskにも被覆0: 109行（うち復元不可16件との重複は0件、新規見落とし無し）
  - mask欠損/空だった椎体: 0件（25件全てmaskは存在・非空10万〜41万voxel）
- 残る **16件は該当bboxが1行も無い**（RSNA元データの欠損、ツール側では復元不可）

## 3. 復元・警告機能の実装

`server.py`:
- `load_fracture_labels` / `_missing_fractured_levels`: train.csv基準で
  「骨折=1かつrunが無い」椎体を検出（対象を該当studyだけに限定、全235 studyの
  再計算は発生しない）
- `augment_with_missing_fractured_levels`: 該当studyのみ全7椎体のbbox内mask
  被覆率をargmaxで比較し、
  - 該当bboxがあればrun_id="supplement", note="coverage_recovered" で追加（9件）
  - 無ければrun_id="missing", note="bbox_missing" の画像なし警告runを追加（16件）
  - 既存の536 runs・保存済み156ラベルには一切変更を加えない（追加のみ）
- `_api_annotation`: bboxが無いrunへの保存はHTTP 400で拒否

`index.html`:
- サイドバー: 黄色「補完」バッジ / 赤「bboxなし」バッジ、run一覧に注記
- グリッド: bbox_missingは画像を出さず警告文のみ表示
- 保存ボタン・region 1-4ボタンをbbox_missingの際disabled（キーボードショートカットも同様にガード）

## 4. 起動速度の問題と対策（キャッシュ）

上記機能追加によりstartup時にNFS越しのDICOMヘッダ・mask(.nii.gz)読み込みが
発生し、起動が3〜4分かかるようになった（元は CSV/JSON のみ読む数秒起動だった）。

対策としてディスクキャッシュを実装:
- `_augmentation_fingerprint`: bbox_csv / metadata_dir / train_csv /
  segmentation_dir の mtime を計算
- `_load_augmentation_cache` / `_save_augmentation_cache`: fingerprintが
  一致すれば `Unet/dicom_bbox_annotation_tool/.cache/missing_level_recovery.json`
  から復元し、mask読み込みをスキップ
- `.gitignore` に `Unet/dicom_bbox_annotation_tool/.cache/` を追加（生成物、非追跡）
